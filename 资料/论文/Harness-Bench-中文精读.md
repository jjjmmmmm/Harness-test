## 第一遍 · 它主张什么（5 分钟）

**问题**：LLM agent 的公开评测要么抽象掉执行层、要么评测整个提交的 agent 系统、要么固定执行环境只比模型——**harness 本身从来没被当成过被测变量**。
**一句话主张**：Agent = Model + Harness；成绩应该在"模型–harness 配置"级报告，而不是只归给底座模型。

**做法**：106 个沙箱化离线任务（8 类工作流），**6 个可配置 harness × 8 个模型后端**全因子矩阵 = 5,088 条轨迹，另加 Codex（模型绑定的 coding agent）106 条作参照，共 **5,194 条**。外部条件全固定（任务、初始沙箱、预算、超时、评测器），各 harness 保持**原生执行行为**。

**发现方向**：① 同任务同模型池下，最高分 harness（NanoBot 76.2）与最低分（OpenClaw 52.4）差 **23.8 分**——配置级差异显著；② 越强的模型跨 harness 方差越小（对执行基底越耐受），弱模型更敏感；③ 失败呈现五类可复现"执行漂移"症状；④ harness 敏感度不均匀——结构化数据/工具编排/工作区操作类任务上最大，纯语言类任务上最小。
**口径（作者自认）**：这是**配置级诊断**，不是对单个 harness 机制的因果分解；是**描述性测量**，不是统计断言（全文没有 bootstrap/置信区间）。

## 第二遍 · 它怎么证明（35 分钟）

> **Step 2 · 基准设计（12 分钟）**
> 🎯 **六个靶子，边读边抄**：
> ① **四要素**：一次评测 = 任务 + 模型后端 + harness 配置 + 沙箱环境 + 评测器（评测器在 agent 外部，看完成的工作区打分）。运行写作 `R = Run(M, H, E, T)`，`TaskScore = Eval(R; J)`。
> ② **任务集**：106 个本地沙箱任务，每个都要产出**交付物（deliverable）**，配 oracle 或 rubric 从最终工作区状态判定；manifest 含 prompt 序列、fixtures、评测器、超时、类别、标签。
> ③ **四条准入标准**（每个候选任务人工评审）：**Realism**（像真实用户工作流）、**Solvability**（用给定沙箱资源可完成）、**Oracle-checkability**（成功可由确定性检查或明确 rubric 判定）、**Integrity**（agent 不能靠偷看隐藏答案、改受保护 fixtures、绕过约束拿分——**反作弊条款**）。
> ④ **运行协议**：setup（渲染任务、建环境、全新沙箱）→ execution（按预算和约束执行；全程记录模型请求/响应、工具调用、工作区变更、用量，重构成统一轨迹）→ judge（评测器检查最终工作区与执行证据；参考答案和评测脚本对 agent 不可见）。
> ⑤ **评分公式**：`TaskScore = Security × Completion × Process`，其中 `Process = (Robustness + ToolUse + Consistency) / 3`，`Security ∈ {0,1}` 是二进制闸门（未授权访问、泄密、违禁动作→直接 0 分）；非二进制分都归一到 [0,1]。**乘法是刻意保守的**：拿高分必须"完成 + 无安全违规 + 执行行为可靠"三者同时成立。过程分由固定外部 LLM 裁判（claude-sonnet-4.6）按 rubric 打。
> ⑥ **控制表（Table 1）**：固定 = 任务 prompt 与 fixtures、初始沙箱、预算/超时/评测器；变动 = 模型后端 × harness 配置（因子矩阵）；**保持原生** = 提示与动作格式、工具接口与状态策略、重试与恢复行为；权限与工具 = 只开最小必需集。
> 📕 **核对点 ①**：翻 PDF **Table 1**——抄"Native to each harness"那三行（这是它和 Scaffold Effect 最大的不同：Scaffold 固定提示词，HB 连提示词都不固定、保持原生）。再看 **Figure 2**：抄 8 个类别名和各自任务数（SE 22 / Workspace 15 / Data BI 14 / Knowledge 13 / Office 12 / Vertical 12 / Long-running 11 / SRE 7）。
> ✅ **自查**：不看译文写出评分公式，并说出"为什么用乘法不用加法"。

### 【译文 · 3 基准设计（节译）】

Harness 指"条件化模型调用、把模型输出转化为外部工作区动作"的系统层，可含提示模板、动作格式、上下文构建、工具调用、工作区访问、权限、预算控制、追踪与恢复。这些机制在真实系统里彼此耦合，所以 **Harness-Bench 评测完整的 harness 配置，而不是拆开单个机制**。环境与评测器都在 agent 外部。对每个任务和模型后端：固定面向用户的任务、初始沙箱、预算、超时、评测器，只变 harness 配置——**不强迫所有系统进同一种内部策略或运行时**，每个 harness 以原生执行行为跑在同一任务资源和评测协议下；因此测量应解读为"模型–harness 配置级的诊断"，而非"单个 harness 机制的因果分解"。

> **Step 3 · 实验与主结果（10 分钟）**
> 🎯 **四个靶子**：
> ① **矩阵**：106 任务 × 6 可配置 harness × 8 模型后端 = 5,088 条轨迹；+Codex 106 条（模型绑定、单列不进矩阵）= 5,194。每个 harness 从默认配置出发，只启用完成任务所需的最小权限和工具集。
> ② **模型后端 8 个（附录 B Table 5，照抄）**：anthropic/claude-opus-4.6、anthropic/claude-sonnet-4.6、google/gemini-3.1-pro-preview、qwen/qwen3.6-plus、**z-ai/glm-5.1**、moonshot/kimi-k2.5、openai/gpt-5.4、**deepseek/deepseek-v4-flash**——注意最后这个：**腾讯项目固定的 DeepSeek 就在矩阵里**。
> ③ **主结果（Table 2）**：可配置 harness 里 NanoBot 最高 76.2、OpenClaw 最低 52.4，**同任务同模型池下差 23.8 分**；且 NanoBot 用比 Hermes/ZeroClaw/NullClaw/Moltis 更少的 token 拿到最高分——**轨迹更长 ≠ 表现更好**。Codex 80.4 很强，但它是模型绑定的专用栈，只作"实用参照点"，不作受控消融。
> ④ **harness 敏感度（Figure 3 + 附录 C）**：强模型 = 高均值 + 低跨 harness 方差；弱模型方差大（对执行基底更敏感）。**类别级不均匀**：Data BI & Finance Analytics（方差最大）、Workspace/Tool Use、Software Engineering 上 harness 影响最大；Office & Business Communication 最小——**任务越是依赖"推理-工具-状态-可验证产物"的对齐，harness 越重要；纯语言任务最不敏感**。
> 📕 **核对点 ②**：翻 PDF **Table 2**——抄 NanoBot 和 OpenClaw 两行完整数字（Score/Comp/Secur/Tool/Cons/Rob/Tok/Turns）；再看 **Figure 3** 左图，确认"强模型方差小"的形状。
> ✅ **自查**：说出 23.8 分这个差距"同什么、不同什么"（同任务同模型池，只不同 harness 配置）。

### 【译文 · 4 实验（节译）】

我们将 Harness-Bench 用作模型–harness 配置的诊断协议。主评测 6 可配置 harness × 8 API 模型后端在 106 任务上的全因子矩阵；每条轨迹 = 固定任务 × 模型后端 × harness 配置下的一次完整尝试。过程评估用 claude-sonnet-4.6 作固定外部裁判。Table 2 按 harness 汇总：可配置组中 NanoBot 76.2 最高、OpenClaw 52.4 最低，同任务集与模型池下 23.8 分的差距表明配置级差异显著；高分 harness 过程分（工具恰当性、一致性、健壮性）也更强——我们视之为**诊断信号而非因果解释**。token 与轮数同样分化：NanoBot 以少于四个对手的 token 拿到最高分。harness 敏感度分析：对每个模型后端算其在各 harness 上的均分方差——强后端方差小，弱后端方差大。Codex 用 GPT-5.4、成绩有竞争力且胜过多数 GPT 背书的可配置 harness，但略低于 NanoBot+GPT；因模型绑定，只作实用参照。三条解释边界：评测的是完整 harness 配置；聚合分含 LLM 辅助过程评估；结果是固定任务集上的描述性测量，不是对所有 agent 工作流的统计断言。

> **Step 4 · 失败分类表（8 分钟，JD 指定重点）**
> 🎯 **先抄表，再看两个模式，最后记框架**。组织原则：按**轨迹在哪里失去与成功条件的对齐**分类；各类**非互斥**（一条轨迹可同时呈现多种症状）；占比 = 该症状在失败轨迹中出现的频率。

| 失败模式 | 占比 | 典型表现（原文直译） |
| :--- | :--- | :--- |
| **Contract / format**（输出契约/格式） | **36.4%** | 违反 schema 或输出契约：畸形 JSON、缺账本行、清单不完整 |
| **Tool / recovery**（工具/恢复） | **24.6%** | 工具报错或命令被拒后，**没有跟有效的恢复或计划修正** |
| **Evidence / grounding**（证据/接地） | **14.6%** | 源覆盖不完整，证据密集任务中常伴**无依据断言或缺失验证** |
| **Artifact commitment**（产物落盘） | **11.1%** | 推理看似合理，却**未提交要求的输出或工作区产物** |
| **State / continuation**（状态/续跑） | **9.3%** | 未保住持久进度，或中断/多轮任务中无法可靠续跑 |

**两个突出模式（原文）**：① 大量失败发生在"语义上看似合理"与"机器可校验输出"的**边界**上——agent 像是懂了任务，却仍违反输出 schema、漏掉要求的账本、交不出可消费的产物；② 大量失败发生在**部分进展之后**——agent 看过相关输入、收到过有用的工具反馈，但轨迹没把进展转化为恢复、有据断言、状态保持或已提交的输出。

**框架两词**：**执行漂移（execution drift）**——失败 = 模型推理与"最终判定成败所依赖的东西"（文件、工具、证据、状态、输出契约）耦合变弱的症状；**执行对齐（execution alignment）**——harness 在多大程度上保持"agent 推理 / 工作区状态 / 工具动作 / 评测器条件"四者的对应。为什么同模型换 harness 成绩会变：**harness 隐式定义了任务的运行时表征**——什么算待办、什么算已观察证据、什么算可恢复失败、什么算完成；表征弱则合理推理漂移出判定条件，执行状态清晰可读则失败能在变成最终判定失败前被发现。
> 📕 **核对点 ③**：翻 PDF **Table 3**——逐行核对五个占比数字；**这是 JD 指定要抄的表**，抄进笔记并给每类自己举一个例子（例子是你写的，表里没有——归因是你自己的工作，表只管对账）。
> ✅ **自查**：五类按占比从大到小背一遍；说出"哪两个模式覆盖了 61%"（契约+恢复）。

### 【译文 · 5 分析（节译）】

聚合分说明 harness 选择能影响成绩，但不解释差异从哪来，所以我们检查轨迹中的复发失败模式。分析用 oracle 结果、过程笔记、失败笔记等结构化字段识别复发症状。Table 3 按轨迹失去对齐的位置组织五类症状。这种框架把"可执行 agent 评测"与"只看最终答案的评测"区分开。§5.2 执行对齐：失败轨迹中对应常这样断裂——工具反馈没进入下一步动作、证据没挂到断言、部分进展没被保持、意图的结果没被提交为合法产物。Harness-Bench 评测的不只是模型推理，还有**把推理带进已验证动作的那套系统**。

## 第三遍 · 哪里不够硬（8 分钟）

> **Step 5 · 批判遍**
> 🎯 **局限（作者自认，§6）**：① 沙箱离线工作流——牺牲了活服务、用户反馈、外部状态漂移、长期生产记忆的覆盖；② 评测的是**完整配置**——观察到的差异只能解读为配置级效应，**拆不到单个机制**；③ 过程分部分依赖 rubric/LLM 裁判——主观性入口；④ 全部是**描述性测量**，无统计检验。
> 🎯 **自己挑刺**：LLM 裁判（claude-sonnet-4.6）本身是个模型——**裁判换模型，过程分会不会变？**（论文用"固定同一裁判"控制了这点，但"裁判模型偏差"没讨论。你的 D3 判分脚本用确定性检查，正好绕开这整类问题。）
> 🎯 **接榫**：它停在"配置级"，腾讯项目往前走两步——**单零件消融**（一次只动一处 = 它没做的因果分解）+ **置信区间与复测**（把描述性观察升级为检验）。
> ✅ **自查**：说出它"最硬的一条证据"（23.8 分差距 + 5,194 条轨迹）和"最大的两个洞"（无因果分解、无统计检验）。

### 【译文 · 6 讨论（要点）+ 7 结论】

**harness 是被测能力的一部分**：agent 成绩应解读为"嵌在执行系统里的模型的属性"，不是底座模型单独的属性——分数度量的不只是模型能推出什么，还有 **harness 让它能观察什么、修改什么、从什么中恢复、验证什么**。**"更强的模型会让 harness 不重要吗？"**：强模型可能减少对提示级脚手架的需求，但仍需要可靠的执行基底——权限边界、持久状态、可读轨迹、证据记录、客观验证。未来基准应同时报告取得分数时的模型与 harness 条件。**结论**：Harness-Bench 通过固定外部任务条件、保留各 harness 原生执行行为，让执行层变异在共享协议下可观察；5,194 条轨迹上的显著配置间差异支持按配置级报告 agent 能力。

## 合卷：答两问（10 分钟，关掉本文件）

**问题 1：它怎么把 harness 从"背景"变成"被测变量"？**（满分 5 要素）
① 固定清单：任务/初始沙箱/预算/超时/评测器全固定；② 变动：模型 × harness 全因子矩阵（6×8×106=5,088）；③ 原生保留：提示格式、工具接口、状态策略、恢复行为不拉平（与 Scaffold Effect 固定提示词形成对照）；④ Agent = Model + Harness，比较单位 = 配置；⑤ 口径：配置级诊断，**不是**单机制因果分解。

**问题 2：失败分类表怎么用？**（满分 5 要素）
① 五类 + 占比（Contract 36.4 / Tool 24.6 / Evidence 14.6 / Artifact 11.1 / State 9.3）；② 组织原则 = 对齐断裂的位置；③ 非互斥（一条轨迹多症状）；④ 两个突出模式：合理≠可校验的边界、部分进展后掉链子；⑤ 用法 = 失败对账单：先归类，再决定归因给谁、用什么证据复测——表不自带"谁的锅"。

## 附录 A · 快读区（摘要 / 引言要点 / 附录 A–D）

**摘要**：LLM agent 越来越多地作为可执行系统部署（用工具、改工作区、产具体产物）。这类工作流里，成绩不只取决于底座模型，还取决于 harness——管理上下文、工具、状态、约束、权限、追踪与恢复的系统层。既有基准要么抽象掉执行、要么比完整 agent 系统、要么固定 harness，使执行层变异难以研究。我们提出 Harness-Bench：在真实 agent 工作流中度量**配置级 harness 效应**的诊断基准——跨多模型后端、在共享任务环境/预算/评测协议下评测代表性 harness 配置，同时保留各 harness 原生执行行为。106 个从实用 agent 使用模式构造、经人工评审的沙箱离线任务；每次运行记录最终产物、执行轨迹、用量统计与校验器输出，支持超越"最终完成与否"的分析。5,194 条轨迹上，完成度、过程质量、效率与失败行为在模型–harness 配对间差异显著——agent 能力应按配置级报告，而非归给底座模型 alone。分析还识别出复发性的**执行对齐失败**：看似合理的推理与工具反馈、工作区状态、证据、可验证输出契约脱钩。

**引言要点**：既有基准（MMLU/GSM8K 等静态；SWE-bench/Terminal-Bench/WebArena/OSWorld 等可执行；AgentBench/GAIA/Claw-Eval 等工作流型）都不直接把 harness 当被测变量。具体系统（OpenClaw、NanoBot、Hermes 等）在工具暴露、上下文策略、状态管理、权限边界、恢复行为上各不相同——harness 工程是真实性能的核心，但既有评测只研究单个系统或固定执行环境下比模型。三大贡献：基准资产（106 任务+manifest+fixtures+评测器+轨迹）、评测协议（固定外部条件保留原生行为的模型–harness 协议）、诊断分析（5,194 轨迹上的完成/过程/效率/失败症状）。

**附录 A**：LLM 使用声明——用于润色文稿、改语法、辅助数据分析与统计汇总；全部科学内容由作者复核。**附录 B**：6 个可配置 harness（OpenClaw、ZeroClaw、Hermes、Moltis、NullClaw、NanoBot——含长驻运行时、研究型记忆/skills、安全本地运行时、轻量运行时等定位）+ 8 模型后端（见 Step 3）+ Codex 单列。**附录 C**：类别级 harness 敏感度（见 Step 3 ④）。**附录 D**：代表性任务卡（工作区设置/目标/预期产物/约束/oracle 判定信号——**你建自己题集时照这个格式写卡**）。

## 附录 C · 与腾讯 Harness 项目的对照（面试可讲）

| Harness-Bench | 腾讯项目 |
| :--- | :--- |
| 固定外部条件，保留原生执行行为，**配置级诊断** | 同方向但更细：**单个零件消融**（一次只动一处） |
| 自认"不是对单个 harness 机制的因果分解" | 项目要做的正是它没做的：零件级因果归因 |
| 5,194 轨迹仍自称"描述性测量，非统计断言" | 项目加的：**置信区间 + 复测闭环** |
| 评分公式 Security × Completion × Process | 你 D3 Block 5 要写的"完成度 × 过程分 × 安全闸门"三层评分标准——**同构来源** |
| 四条任务准入标准（含 Integrity 反作弊） | 你建 8 题实验题集的准入模板 |
| 8 模型后端含 deepseek-v4-flash | 项目固定 DeepSeek——矩阵里有它的独立证据可引用 |
| 失败分类表（五类，按对齐断裂位置组织） | "失败图像 + 归因结论链"的对账单底版 |
| 类别级敏感度：结构化/工具编排类任务 harness 影响最大 | D3 选题参考：**选会压到你换的那个零件的任务**，别选纯语言题 |

**一句话（面试可直接说）**：Harness-Bench 把 harness 立成了评测轴——106 个沙箱任务、6×8 全因子矩阵、5,194 条轨迹，量出同模型池下 23.8 分的配置级差距，并给出按"执行对齐断裂位置"组织的五类失败对账单；但它自认只做到配置级诊断、不做单机制因果分解——腾讯项目正是在它停下的地方接着走：单零件消融 + 置信区间 + 复测闭环。
