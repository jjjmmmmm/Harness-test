## 第一遍 · 它主张什么（8 分钟）

**问题**：公开排行榜按"模型名 + 通过率"给 coding agent 排名，而包裹模型的 harness——负责发工具、管上下文、决定何时停止的那层——要么不披露、要么为了把单行分数刷高而随便换、要么被默认当成"受控常量"。**模型对模型的比较，只有 harness 固定时才有效；harness 一变，性能和效率就把模型效应与脚手架效应搅在一起。**

**做法**：固定任务集（Terminal-Bench Pro 分层抽样 50 题）和模型（Qwen 3.6 Plus、MiniMax M2.5），横向换 3 个开源 harness（Goose、OpenCode、OpenHands-SDK），共 300 次受控试验，全部报 95% 配对任务自助置信区间（B=10,000）。

**四个发现**：
① **通过率侧分不清**：模型内换 harness 的配对通过率差 0–8pp，CI 除最大差距外均含 0——和换模型升级（4–10pp）同量级、都在噪声之内；
② **成本侧分得清且压倒性**：每解一题的 token 消耗，OpenCode ≈ Goose 的 **40×**（CI 完全不重叠，稳健）；换模型升级只动 1.0–1.3×；
③ **失败指纹跨模型复现**：Goose = REASON 主导（卡住就老实认输）、OpenHands-SDK = VERIFY + MAX TURNS（倾向交出"看似完成的错误答案"或耗尽轮数）、OpenCode = TIME + 空转（超时+无动作轮次）——同一 harness 换两个模型指纹不变 → **这是脚手架属性，不是模型属性**；
④ **空转税**：OpenCode 每题平均 2 轮"无动作轮次"（不编辑文件也不发命令，但每轮带着全量上下文计费），是 Goose 的 10×——用户在美元成本之外还要付等待和监督成本。

**结论**：评测的比较单位应是 **harness–模型对**，不是模型名；通过率之外必须并报 token/每解一题、无动作轮次、失败类别向量。作者公开了匿名配置、原始试验日志和分析脚本。

### 【译文 · 2 相关工作（要点）+ 3 实验设置】

**相关工作（要点）**：Terminal-Bench / Terminal-Bench Pro 提供带确定性测试的真实命令行任务（Pro 共 400 题、8 域、每题约 28 个测试）；**SWE-bench 系列注意到了脚手架影响分数，但把它当作"要控制的干扰"，而不是"要研究对象"**——本文反其道而行。前人论证过"agent 是系统不是模型"，但没在固定任务、固定模型下量化过效率影响。Harbor 提供统一评测框架（一份任务清单跑多种 harness），是本文的执行基础设施。

**3.1 任务**。取 Terminal-Bench Pro 公开 200 题中的 50 题，按 8 个领域原型分层随机抽样（GPT-4o-mini 对 instruction.md 分类，各类计数跟随源分布，类内随机抽）。全部任务用 pytest 做确定性判定。

**3.2 模型**。经 OpenRouter 接入两个新近的强力 agentic 模型：**Qwen 3.6 Plus**（混合线性注意力 MoE，常开思维链；Terminal-Bench 2.0 报 61.6，对照 Claude Opus 4.5 的 59.3）与 **MiniMax M2.5**（228.7B 参数 MoE，激活 10B；SWE-bench Verified 报 80.2%）。

**3.3 Harness**。三个设计哲学迥异的开源 coding agent harness：**Goose**——重型 IDE agent，急切地把文件树预注入上下文；**OpenCode**——持久工具循环型，不做自动上下文预载；**OpenHands-SDK**——微 agent 架构，带子 agent 委派、内部重试与显式验证步骤。三者都被 Harbor 原生支持，用完全相同的任务清单运行。

**3.4 标准化协议**。**固定不变**：Terminal-Bench Pro 指令逐字保留；原生测试套件；每题一个 Daytona 沙箱；每次试验 900 秒墙钟上限；统一走 OpenRouter 网关。系统提示词模板在三个 harness 间保持**几乎完全一致**：同样的运行原则、同样的不可妥协项、同一份四技能操作手册（build-and-env / deep-debug / terminal-investigation / test-driven-solve）、同样的任务指令；只有一小段 harness 专属的"Using your tools"和轮次措辞不同。轮数上限：Goose 与 OpenHands-SDK 各 40 轮（经 agent 参数传入）；OpenCode 在 Harbor 中不暴露轮数预算参数，仅受墙钟上限约束。**我们有意把每个 harness 当作"以其原生控制面可部署的系统"来评测——暴露的预算控制本身就是被研究的脚手架的一部分，不是要拉平的干扰参数。** 没有被标准化、从而构成研究对象的，是各 harness 的原生工具 API、自动上下文预载、以及内部重试/子 agent 逻辑。

**3.5 指标**。每次试验收集：是否解决、轮数、token 总量、平均无动作轮次（既没编辑文件也没发新命令的轮，作为监督负担的代理指标）、是否触轮数上限、墙钟秒数，以及六类失败分类（REASON、VERIFY、TIME、MAX TURNS、HANG、ERROR；判定规则见附录 A）。不确定性用 95% 配对任务自助区间（B = 10,000）报告，覆盖通过率与每解一题 token 两项。**token 计账**：OpenCode/OpenHands-SDK 用 harness 报告的 prompt+completion+缓存总量；Goose 只报总量无方向拆分。**每解一题 token = 该格 token 总和 ÷ 该格解决数**（失败与基础设施错误的试验也计入分子——这是部署者每完成一个任务真实吸收的成本，不是成功试验的成本）。全程用 OpenRouter 默认采样参数，不做任何覆盖；工具调用失败不做 harness 级重试；基础设施失败记为 ERROR，计入分母（n=50）但不记解决。

> **Step 3 · 结果：四个发现（20 分钟）**
> 🎯 每个发现问三遍：**跟谁比？差多少？这数字为什么重要？**
> - **发现 1**（4.1）：通过率——模型内 harness 极差 2–8pp；模型间极差 4–10pp。两两配对差：最大 -8pp（Goose vs OpenCode @MiniMax），其余 -2pp、0pp。**n=50 下大多数配对差异统计上与 0 不可区分**；
> - **发现 2**（4.2）：每解一题 token——排序两个模型完全一致：Goose < OpenHands-SDK < OpenCode；OpenCode ≈ Goose 的 40×；**token 侧 CI 完全不重叠**（Goose 上界 61K ≪ OpenCode 下界 733K），量级差对自助不确定性稳健。且差距不来自跑更多轮（轮数只差 1.2×），来自**每轮的上下文膨胀与工具序列化**；
> - **发现 3**（4.5）：失败指纹——三个 harness 各有主导失败模式，且**换两个模型都复现**（这是"脚手架属性非模型属性"的直接证据）；

### 【译文 · 4 结果】

**4.1 通过率**。Table 2 报每格通过率与 95% 配对任务自助 CI。模型内，harness 极差 2–8pp；harness 内跨模型极差 4–10pp。配对差异及 CI：最大 -8.0pp（Goose vs OpenCode @MiniMax，[-18.0, 0.0]）、-2.0pp（Goose vs OpenCode @Qwen，[-12.0, +8.0]）、0.0pp（OpenCode vs OpenHands-SDK，两个模型都是）。**在 n=50 下，大多数配对通过率差异与零统计不可区分。**

**4.2 每解一题 token 成本**。Table 3 为主效率指标。两个模型排序完全一致：Goose < OpenHands-SDK < OpenCode。OpenCode 每解一题 token 约为 Goose 的 **40×**，而通过率差保持在上述 0–8pp 内。差距不是 OpenCode 跑更多轮：平均轮数 21–27 vs 18–25（1.2×，远在 40 轮上限内）——**更多来自每轮的上下文增长、工具序列化与 harness 各自的 token 计账**。自助稳健性：每解一题 token 的 95% CI 为 Goose@Qwen [21K, 40K]、Goose@MiniMax [25K, 61K]、OpenHands@Qwen [610K, 1.21M]、OpenHands@MiniMax [537K, 1.35M]、OpenCode@Qwen [733K, 1.84M]、OpenCode@MiniMax [1.01M, 2.50M]。Goose 的 CI 上界远低于 OpenCode 的 CI 下界，**量级差对自助不确定性稳健**。

**4.3 帕累托前沿：通过率 vs token 成本**。Figure 1 把两轴画在同一面板。Goose 在两个模型上都落在帕累托前沿（没有点在"成本更低且通过率不低于它"的位置上）；OpenCode 在两个模型上都被支配（被 Goose 以接近的通过率在成本上支配、被 OpenHands-SDK 以相同通过率在成本上支配）。**通过率散布很小（38–50%），成本散布是两个数量级。**

**4.4 无动作轮次**。OpenCode 平均每题 2.0–2.16 个无动作轮次，Goose 为 0.2–0.3，**10× 比值跨两个模型复现**。每个无动作轮次因消息历史累积都携带全量上下文窗口的输入 token——平均位置在第 10 和第 20 轮附近的两个空转轮，各自就能烧掉数千 token。我们把它框架化为**每题空转税**：交互式使用 OpenCode 的开发者同时吸收美元成本与墙钟延迟。预算敏感性检查：有轮数记录的 OpenCode 试验中 88%（Qwen）/71%（MiniMax）低于 40 轮，最大 67–69 轮；若加 40 轮上限会截断 12–29% 的试验且多在失败尾部。**40× 差距不来自跑飞了，来自每轮的 token 体量。**

**4.5 失败模式指纹**。Table 4 报六类失败计数。三个清晰指纹浮现，**且跨两个模型复现**：
- **Goose：REASON 主导**（Qwen/MiniMax 各 20/15 个 REASON，VERIFY 为零）。卡住时 Goose 宁可停手也不交错误答案；低无动作轮次（0.2/0.3）证实其行动果断。
- **OpenHands-SDK：VERIFY + MAX TURNS**（6/8 VERIFY、6/6 MAX TURNS；触上限计数 8/9 高于 MAX TURNS 分类数 6/6，因为"触上限同时抛异常"的运行按决策树被归入 HANG）。倾向"奔向收尾"：交出看似合理的错误方案，或耗尽迭代轮数——用户必须更仔细地验收。
- **OpenCode：TIME + 空转**（5/10 TIME、4/1 HANG、VERIFY 为零）。OpenCode 经 Harbor 不暴露轮数预算参数，所以永远不产生 MAX TURNS——在另外两个 harness 下会表现为 MAX TURNS 的运行，在这里以 TIME 或 HANG 面目出现。它只肯交通过测试的方案（VERIFY 零），代价是时间与 token；**它的正面结论可以信任**。

**4.6 分类别通过率**。Table 5（两模型合并）。差异大多很小，但一处醒目：**IMPL（从零实现）上 OpenHands-SDK 大幅领先（69% vs Goose/OpenCode 各 38%）**——子 agent 架构的特长场景。三个 harness 在 SEC 上都挣扎（8–17%），SYS 全军覆没（0%）。其余类别 harness 排序不稳定——**给"分类别排行榜"敲警钟**。

**4.7 harness 效应 vs 模型升级效应（Table 6，全文总账）**。通过率：harness 0–8pp vs 模型升级 4–10pp——同量级、n=50 下都在自助噪声内。**成本侧不对称是压倒性的：harness 选择让每解一题 token 动 40×，升级模型几乎不动（1.0–1.3×）。** 失败画像：harness 换出指纹，模型升级指纹不变；无动作轮次：10× vs <1.1×。

## 第三遍 · 哪里不够硬（10 分钟）

> **Step 4 · 批判遍：讨论与局限**
> 🎯 **§5.3 建议清单（它建议别人做什么）**：比较单位改为 harness–模型对；通过率之外并报三个一等公民指标——每解一题 token、平均无动作轮次、失败类别向量。
> 🎯 **§6 局限（它自己承认什么）**：n=50（1 题 = 2pp，若干效应在自助噪声内——作者原话"**当描述性结论看，而非统计上定论**"）；token 计账不对称（Goose 无输入/输出拆分，40× 由总量锚定、稳健）；轮预算不对称（"轮"由各 harness 自定义）；3 harness × 2 模型，外推要谨慎；供应商默认参数会漂移。
> 🎯 **自己挑刺（对着原文数字）**：摘要说"CI 含 0，除最大差距外"；但正文里那个最大差距（-8pp）的 CI 是 [-18.0, **0.0**]——**恰好触 0**。触 0 算"不含 0"吗？论文自己留了个边界含糊处，笔记里记一笔（这正是"先看 CI 再说话"的活例子）。
> 🎯 **接榫**：这篇只换**整个 harness**，从未拆到 harness 内部的单个零件——组件级归因是它没做的一步，正是腾讯项目要走的下一步（对照 `mission.md` 第二句）。
> ✅ **自查**：能说出"最硬的一条证据"（token 侧 CI 不重叠的 40×）和"最大的一个洞"（n=50 只算描述性 + 只到整 harness 粒度）→ 过。

### 【译文 · 5 讨论（要点）+ 6 局限 + 7 结论】

**5 讨论（要点）**。40× 对真用户意味着三件事：**美元成本**（同模型同任务 40× API 开销，压倒当前最强模型之间 1–2× 的价差）；**墙钟时间**（空转轮不是静默的，每个都是用户要等的一轮往返）；**监督负担**（"同一文件重读三遍"对模型便宜、对人贵）。三类指纹各对应一种监督纪律：Goose 给你诚实的"我做不到"；OpenHands-SDK 需要你仔细验收；OpenCode 的正面结论可信但你付时间。5.3 建议：排行榜应以 harness–模型对为评测单位，通过率旁并报每解一题 token、无动作轮次、失败类别向量——只按模型名报通过率，把两个独立方差源搅在一起，还丢掉了决定可部署性的成本与监督信号。

**6 局限**。样本量：n=50，1 题对应 2pp，若干通过率效应在自助噪声内——**当描述性结论看，非统计定论**。token 计账不对称：Goose 经 Harbor 不报输入/输出拆分；40× 由总量锚定故稳健，但按方向的比较对 Goose 不可得。轮预算不对称：Goose/OpenHands-SDK 有 40 轮上限，OpenCode 只有墙钟；"轮"本身由 harness 定义。三个 harness、两个模型：harness 特异性发现不应假设推广到所有脚手架架构或闭源产品。供应商默认会漂移：精确复现需锁定运行时的路由与采样设置。

**7 结论**。受控证据表明：harness 选择带来 40× token 成本差与 harness 特异失败指纹，配对通过率最多移 8pp；两者都在两个模型上独立复现。以人为中心的评测单位应是 **harness–模型对**，并随通过率报成本、空转与失败模式信号。配置、原始日志、快照、分析脚本全部公开。

## 附录 A · 快读区（译文：摘要 / 引言 / 相关工作细目 / 附录）

**摘要** — 公开的 coding agent 排行榜通常按"模型名 + 通过率"排序，而包裹模型的 harness——负责发工具、管上下文、决定何时停止的脚手架——往往语焉不详。harness 固定时模型对模型的比较才有效；harness 变动时，性能与效率就把模型效应和脚手架效应搅在一起。我们在 Terminal-Bench Pro 的分层 50 题子集上、跨三个开源 harness（Goose、OpenCode、OpenHands-SDK）评测 Qwen 3.6 Plus 与 MiniMax M2.5。harness 选择使每解一题 token 相差高达 40×，而模型内配对通过率差异保持在 0–8pp（95% 配对任务自助 CI 除最大差距外均含 0）。失败指纹跨模型复现（Goose 为 REASON、OpenHands-SDK 为 VERIFY/MAX TURNS、OpenCode 为空转/TIME），表明这是基本独立于模型的 harness 级偏差。对以人为中心的评测而言，模型名单独作为比较单位是不完整的：**harness–模型对**才决定真实成本、延迟与监督负担——无动作轮次是每题等待税而不只是 token 税。我们建议在 token/延迟预算下按通过率选择 harness–模型对，并在任何模型比较旁报告 token 用量、延迟与完整 harness 规格。匿名配置、原始试验日志、聚合快照与分析脚本已公开。

**1 引言（要点）** — 榜单成了追踪 AI 软件开发进展的主战场，但它们按模型名排名，harness 不披露、或为刷分而变、或被默认当受控常量。从以人为中心的视角：开发者关心的是"每解决一个任务的成本、完成耗时、需要多少监督"——这些从纯模型分数里一样都拿不到。直觉并不新：Terminal-Bench 2.0 报告过 Claude Opus 4.5 换 harness 从 52.1% 到 57.8%，输入 token 却从 256.9M 降到 3.9M——**5.7 个点的提升伴随 65× 的 token 差**。本文把这类观察系统化为受控研究：模型固定、只动 harness，差异有多大、是什么性质。四条贡献：① 300 次试验量出 40× 每解一题 token 差、配对通过率差 0–8pp（CI 除最大差外均含 0）；② harness 特异失败指纹跨两模型复现 → 脚手架属性；③ 无动作轮次作为成本差机制的代理指标，框架化为人的监督税；④ 主张比较单位应为 harness–模型对，并公开匿名配置与原始数据。

**2 相关工作（细目）** — Terminal-Bench：真实命令行任务（编译、环境搭建、迭代调试）；Terminal-Bench Pro：400 题 8 域、每题约 28 测试。SWE-bench 及后继注意到脚手架影响分数，但当作"要控制的干扰"而非"要研究的现象"。Wang 等（2024）主张 agent 是系统不是模型，但未在固定任务固定模型下量化效率影响。OpenHands 平台论文（可组合 SDK）、Goose（原 Block 公司）、OpenCode（广泛部署的开源 agent）。Harbor：统一评测框架，单份任务清单支持多 harness——本文执行基础设施。token 效率此前只系统研究过长文本基准，未系统研究 agentic 评测；DL4C"交互感知基准"征集恰要求超越任务完成度的指标（交互质量、监督负担、可验证性）。

**附录 A · 失败分类决策树（D3 给失败样归类直接抄用）** — 异常优先，按序判定：① 有异常按类型映射：AgentTimeoutError（900 秒墙钟触发）→ **TIME**；NonZeroAgentExitCodeError / AgentSetupError → **HANG**；DaytonaAuthorization / EnvironmentBuild / RewardFileNotFound / 解析错误 → **ERROR**。② 否则 solved=true → **SOLVED**。③ 否则触轮数上限 → **MAX TURNS**（仅 Goose 与 OpenHands-SDK 传入轮上限，OpenCode 永不产生此类）。④ 否则 finish_called=true（声称完成但验证失败）→ **VERIFY**。⑤ 其余 → **REASON**（未声称完成即自愿停手）。无单独墙钟阈值；TIME 仅由 AgentTimeoutError 触发。20% 随机抽样经人工复核一致性。
