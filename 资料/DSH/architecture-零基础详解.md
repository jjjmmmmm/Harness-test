## 1. 这篇文档是什么，为什么 JD 点名它

`architecture.md` 是 DSH 仓库的**总设计图**。项目方让你读它，是因为"拆解表 + 对照组"的前提是**先知道有哪些零件，才能谈'一次只换一个零件'**。

> **Step 1 · 前置概念：5 个词（8 分钟）**
> 🎯 5 个词每个都能用自己的话说一句才算过：

### harness（执行层）
模型本身只会"文本进 → 文本出"。读文件、跑命令、记住之前的事、错了重试——全是模型外面那层包裹干的活。这层包裹就是 harness。DSH 就是一个开源 harness。

### plugin（插件）
DSH 的口头禅是"Everything is a Plugin"：**产品的每一部分都是插件**——原文原话点名：模型适配器、工具注册表、会话日志，以及 **agent loop 本身**。"每个都可以从配置替换"。"连主循环都是插件"意味着：循环本身也是合法的实验变量。

### Cordis（底座框架）
插件总得有个地方"插"。Cordis 就是那块插板：每个插件向一个**共享上下文**（`ctx` 大对象）贡献服务、类型化事件和**可逆的副作用**；插件拔掉时，它贡献的东西自动撤销。记住：**看到 `ctx.fs`、`ctx.shell`、`ctx.llm`，就理解为"某个能力挂在 ctx 上的插槽名"**。

### seam（接缝 / 能力插槽）
一个 seam = 一项**可替换的能力**，三个角色：
- **Service Definition**（接口声明）：这个能力"长什么样"；
- **Service Provider**（实现方）：真正干活的（文件系统能力可以是"本地磁盘/沙箱磁盘/远程 SSH"）；
- **Consumer**（使用方）：通常是面向模型的工具。

**题眼**：只要换掉 Provider，整个能力就换了，使用方一行代码不用改——"每个只改一处"在工程上可行的原因。原文还有一句升级版：**文件系统与进程提供方共享同一个执行世界**——把它们指向远程沙箱，Bash、PTY 和 LSP 会**一并**搬过去，无需提供方专用 fork。

### profile 与 patch
- **profile**：具名"组装清单"。原文交付的模板共 **5 个**：`web`、`headless`、`sdk`、`sdk-minimal`、`acp`。
- **patch**：按 **id** 定位某个条目并**替换其整个 config**（或插入新条目）。
- 叠加顺序：**组合包们（按 profile 列出的顺序）→ profile 的 cordis.patch.yml → home 级那份 → 命令行 --patch**。
- 🎯 **实验相关的新细节**：原文说 `web` 用实时重载 patch，但 **`headless`、`sdk`、`sdk-minimal`、`acp` 只在启动时应用一次所有配置层**——所以做实验改完 patch 必须**重启进程**，改了不生效先想这条。

**这对你意味着**：对照组的"只改一个零件"= 两组用同一个 profile，其中一组多挂一条 patch，**patch 里只改一个条目**。

> ✅ **自查**：不看本文件，说出 seam 的三个角色 + "换哪个角色 = 换零件"。

> **Step 2 · 逐节白话：组装机制与核心包（5 分钟）**

### 「Profile 与组合包」
组合包（bundle）= 插件配置 + 挂载代码的分发格式。`dsh-base` 是公共第一层（模型适配器、工具、持久化、**沙箱与审批策略**、设置、凭据、遥测）。`dsh-headless` 在底座上加"不带服务器的一次性运行器"——**做实验主要用它**。

**必会命令**（原文给的，注意实验时把 web 换成 headless）：
```sh
dsh --profile headless --dump-config
```
它打印你机器上实际生效的整棵配置树。**原文原话："它打印出的任何条目，都可以由你自己的 patch 替换"**——这就是实验可行性的合同。做实验前先 dump 一份当基线。

> 📕 **核对点 ②**：在原文里找到上面那句原话（加粗/独立成句），逐字抄进笔记——这是你 D3 实验设计文档里要引用的"合同条款"。

### 「核心包」
| 包 | 干什么 | `ctx` 键 |
| :--- | :--- | :--- |
| core/session | 只追加的会话事件日志 | `ctx.sessions` |
| core/system-prompt | 提示词片段 + 工具 schema 组装 | `ctx.systemPrompt` |
| core/tools | 工具注册表 + 带把关的执行流水线 | `ctx.tools` |
| core/agent / core/agent-loop | Agent 接口 / 实现该接口的默认驱动器 | `ctx.agents` / `ctx.agentLoop` |
| llm/llm | 消息与流式词汇表 + 适配器 seam（接 DeepSeek 在这里） | `ctx.llm` |

> **Step 3 · 事件与轮次流程（5 分钟）**

### 「事件」三类
- **会话事件**：持久事实，追加进日志（"模型看到过什么"全在这）；
- **Agent 事件**（`agent/*`）：进行中的工作（inbox、步骤、状态、请求、验证、续跑）；
- **能力事件**（`fs/*`、`tools/*`、`telemetry/*`）：往某个 seam 上挂策略用。

### 「轮次流程」——DSH 版的 agent 循环
| 你的 mini loop | DSH 的说法 |
| :--- | :--- |
| 一轮循环 | 一个**步骤**（step）= 一次模型请求 + 它调的工具 |
| 整个任务 | 一个**轮次**（turn）= 零或多个步骤 |
| 发消息给模型 | 组装提示词段 + 工具 schema → 每次请求前**从日志"派生并冻结"模型历史**（重试不重复组装） |
| 解析并执行工具 | `tool/call → tools/pre-execute → tools/execute → tools/post-execute → tool/result`（执行前后都有把关事件） |
| 把结果拼回历史 | 结果作为会话事件**追加进日志**，下一步再从日志投影 |

**注意**：DSH 的模型历史不是内存里的一条 list，而是**从会话日志投影出来的**。

> 📕 **核对点 ④**：翻到原文「轮次流程」的代码块——找到 `tool/call*` 到 `tool/result*` 那一行，确认事件链顺序与本表一致；再看代码块上一段，确认"步骤/轮次"的定义。

> **Step 4 · 会话日志：本项目最重要的一句原则（3 分钟）**

> **"模型可见即已记录"**（原文黑体原则）：抵达模型请求的一切都必须能从日志重建，**并由一项运行时不变量断言这一点**；要给模型看新东西，必须新增一种会话事件。

为什么重要：你做归因时，**证据就在会话日志里**。文件名两代格式：v0 是 `session.jsonl[.zstd]`，**v1 及以后是 `session.vN.jsonl[.zstd]`**。你可以说"第 3 步模型看到的报错是完整/被截断的"，并拿日志当铁证——证据链的原料。

> 📕 **核对点 ⑤**：在原文「会话日志」一节找到那句黑体原则和两种文件名，抄进笔记。
