> **Step 0 · 准备（2 分钟）**
> 左开本文件，右开原文。带着一个疑问读：**我是去做评测的，为什么 JD 让我读 DSH 的测试策略文档？**——因为 DSH 团队怎么保证"测试本身可信"，正是你怎么保证"评分尺子可信"的范本。

## 1. 先建立一个意识：测试 = 评测的同构问题（2 分钟）

| DSH 团队的问题 | 你的问题（腾讯项目） |
| :--- | :--- |
| 怎么证明我的 harness 改动没把产品改坏？ | 怎么证明这个 harness 零件造成/没造成失败？ |
| 单元测试全绿，产品却坏了怎么办？ | 30 题全通过，harness 就没问题了吗？ |
| 测试框架（runner）自己可信吗？ | 评分脚本/判分器自己可信吗？ |
| flaky（时好时坏）的测试怎么归因？ | 跑分差异是真实差异还是运气？ |

带着右列的问题去读，每一条都会变得亲切。

> **Step 1 · 测试七层（6 分钟）**
> 🎯 记住七层的**名字和一句话职责**即可，命令不用背。

| 层 | 白话解释 | 对应你的什么 |
| :--- | :--- | :--- |
| **单元测试** | 最小零件逐个测；每个注册表都有"卸载后清理干净"的测试 | 你的自动检查脚本的每个判分函数 |
| **覆盖率门禁** | 按文件 100% 行覆盖；原文明说：**行覆盖是必要条件，永远不是充分条件**（未覆盖的行往往是该删的死代码） | "30 题都跑过"≠"评测有效"——同构警告 |
| **真实 API e2e** | **带真 key 调真模型**；没 key 自动跳过，不阻塞他人 | 你的实验就是"带 key 的 e2e" |
| **预期输出** | 无 key 的组装级预期对比 | 你的"标准答案"文件 |
| **性能基准** | 耗时/内存预算，超了不让合入 | 你的 token 成本对比表 |
| **快照测试** | **录一段真实会话**（输入+模型回放+产物）当预期值，改动后回放对比；workspace 产物独立比对整目录，record/refresh 绝不改写预期 | 你的"配准对照组"：固定一切，只动一个变量 |
| **Web 浏览器快照** | UI 层对比；CI 强制只读回放，**绝不写入预期输出** | 评分标准一旦定稿，跑分时不能顺手改尺子 |

> 📕 **核对点 ①**：翻到原文「层级」一节——数一数是不是七层；把覆盖率那层的"必要条件，但永远不是充分条件"逐字抄下来。

> **Step 2 · 三条可直接搬进报告的原则（10 分钟，全篇最值钱）**
> 🎯 每条原则 = 一句原文引文 + 你的评测版转译。

### 原则一：优先真实实现，而非 mock
> 原文：只 mock 开销高或不确定的边界（LLM 适配器、网络、时钟）；下游一切保持真实。手写替身只能证明"桥接层在搬运字节"，不能证明交付的工具行为符合断言。

**你的版本**：判分不要"让 AI 看着像对"，检查脚本要真的执行/读取产物（跑测试、读文件、比对结果）。你 mini 项目里"声明须有脚本兜底"的纪律与此同源。

### 原则二：验证外部世界，而非自我报告
> 原文：e2e 断言应重新运行命令或从外部重新读取文件；**对 agent 自身输出做关键词探测，会让作弊的 agent 通过**。断言未修改的文件逐字节一致。

**你的版本**：检查脚本必须**重新读磁盘上的结果文件**判分，绝不能解析 agent 的"我已完成"——agent 会说谎（或幻觉）。"未动过的文件逐字节一致"还能直接抓"agent 顺手改了别的东西"——控制变量洁癖的自动化版本。

### 原则三：带真 key 的冒烟测试最值钱
> 原文：**"我们是 DeepSeek，不要吝惜真实 API 测试。"** 无密钥测试只能证明底层通路；价值最高的是冒烟测试：启动已交付的 profile、发送一条提示词，并检查外部世界——它们能捕获「单元测试全绿、产品却坏了」这类 mock 无法发现的问题（原文引了一篇真实事故复盘 0001 背书）。

**你的版本**：别在玩具数据上把检查脚本调通就完事——先跑 2 道真题（真 API、真产物）冒烟，确认"尺子在真实世界里量得出对错"，再放全量 8 题 × 8 次。

> 📕 **核对点 ②**：三条引文各抄一句进笔记（尤其原则二那句"会让作弊的 agent 通过"——面试引用率最高）。

> **Step 3 · 隐藏彩蛋：flaky 的归因（4 分钟）**

原文的硬话（逐字）：

> 把「只有单独运行时才通过」的 spec 读作**该 spec 的缺陷**，而不是 runner 不稳定。

背景：他们的测试隔离**只隔离进程**——端口、可预测路径、外部命名空间、继承的子进程都不隔离，所以要"为每个占用的资源负责到它的 teardown"。

**你的版本**：同一配置跑 8 次结果抖动大时，第一反不该是"模型不稳定"，而是"我的实验环境没控干净"（工作目录没重置？上次文件污染了这次？）。**先怀疑自己的尺子和实验台，再怀疑被测对象**——这半句原样写进你报告的"局限"节。

> 📕 **核对点 ③**：在原文「spec 如何被执行」一节找到那句 flaky 引文和"被隔离的只有进程"那句，抄下来。

## 2. 读后自测

1. 为什么"对 agent 输出做关键词探测"会让作弊的 agent 通过？你的检查脚本怎么避免？（要点：agent 输出是自我报告；改为读磁盘产物/重跑命令）
2. 快照测试和你的"对照组"思想上哪里相同？（要点：录制预期 + 固定一切可固定的，差异只剩主动动的那个变量；绝不改写预期）
3. "行覆盖率 100% 但永远不是充分条件"对应你 30 题压测库的哪个警告？（要点：全跑过≠评测有效）
4. 同配置第 5 次运行突然失败，按本文纪律你的排查顺序？（要点：先查自己的隔离/teardown/目录重置，再谈模型）
5. 交付物 |4| 要求"先证明尺子靠谱"——列出你要做的 3 件事。（要点：原则一/二/三各对应一件：真实判分、外部验证、真题冒烟）
